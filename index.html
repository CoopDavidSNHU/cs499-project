My Journey Through the Program

Finishing this program and building my ePortfolio helped me see what I'm good at and where I want to go. I'm interested in IT support, data analysis, and eventually software engineering. What ties those together is that I like making sure data and software can be trusted.

A few courses outside my artifacts shaped that. In CS-320, I learned JUnit testing, which taught me that code that runs isn't necessarily correct. Testing normal input, edge cases, and bad input is part of the job. In DAT-325, I learned data validation, and in DAT-375, I learned data analysis techniques. Both were part of my data analysis concentration, and they gave me a much better understanding of the data I'll work with in any of the roles I'm aiming for.

While I haven’t specifically coded with other people, I've worked with a team in my Data Analyst Internship to help out the departments of Maverik handle and translate their data. There I built data dashboards using Google Looker, SQL, and Excel to turn messy data into something the non-technical teams could read and use. I had to figure out what information they needed and present it clearly, and that taught me that my work is only useful if the people I'm working with can understand it.

While I haven't worked with a client directly on a project, I understand what it takes for a client to be satisfied with my work. For example, a small business owner asks me for a way to track customer orders. They probably won't know terms like "database" or "query," so I'd focus on what they need to do, such as finding an order or seeing what's late. I'd explain my choices in plain language and check in with them as I go, so I'm not guessing what they want.

For the data structures and algorithms I’ve worked with, I learned to choose a data structure or algorithm that fits the problem instead of just picking whatever works. I think about how much data there is and how the program will really be used. With that being said, when it comes to software engineering and databases, I've learned to organize code so each part has a clear job, and to improve existing code without starting over. I've also worked with databases from the code side and the data side, and my data analysis concentration helped me see why well organized data matters. I also try to build security in from the start. That means keeping passwords and credentials out of the code, controlling who can see what data, and validating input so bad data doesn't get through and is handled properly.

My three artifacts come from two projects that I chose to enhance instead of rewriting. I did this because in a real job you'll often improve existing code, so I wanted to show I can find weaknesses and fix them. Each artifact covers a different area of computer science.

Software Design and Engineering (Android Weight-Tracking App): This Java app tracks daily weight and supports registered and guest logins. I added consistent session management so each user's data follows them from login to display, and guest data is cleared when the session ends. I also changed weight entries into structured records so deleting uses a stored ID instead of reading the screen text.

Algorithms and Data Structures (Same Android App): I replaced parallel lists with a collection of WeightRecord objects and added insertion sort to show weight history from oldest to newest. Insertion sort's O(n^2) worst case is fine for the small number of entries someone logs, and it keeps the code simple.

Databases (Python/MongoDB Animal Shelter Dashboard): This dashboard displays shelter data from MongoDB. I moved credentials into environment variables, added indexes on commonly filtered fields, and replaced Pandas filtering with a server-side aggregation pipeline. This one connects most to my data analysis background because it's about getting the right data efficiently and securely.

Together, these artifacts show that I can write and organize code, pick fitting algorithms, work with databases, and think about security. They also show how I approach improvements. I can better understand what's there, make a focused change, and test that it works. The sections below walk through each artifact in more detail.

Weight Tracker Android App

Java, Android Studio, SQLite

An Android app where users register or log in (or continue as a guest), record their weight each day, and receive SMS notifications. Data is stored in SQLite through a DatabaseHelper class. The main screens are LoginActivity, DataDisplayActivity, and SmsPermissionsActivity.

Enhancement 1: Software Design and Engineering

Narrative for Enhancement 1: https://github.com/CoopDavidSNHU/cs499-project/blob/main/assets/Module-3-Assessment-CS-499.pdf

The original app opened the weight screen without knowing who was using it, so every account and every guest read and wrote the same rows. I added a UserSession class that owns the answer to "who is logged in." Exactly one session is active at a time, it is created only by a successful login or a guest login, and it is cleared on logout. LoginActivity establishes the session before DataDisplayActivity opens, and the weight screen loads only that user's records and deletes by the ID stored on each WeightRecord instead of parsing text from the screen. Guest data is temporary and is cleared when the session ends.

UserSession.java (comments trimmed)

public final class UserSession {

    // User ID used for rows that belong to a temporary guest session
    public static final int GUEST_USER_ID = -100;

    /// This means no one is logged in
    public static final int NO_USER_ID = -1;

    private static UserSession instance;

    private int userId = NO_USER_ID;
    private String username;
    private boolean guest;

    private UserSession() {
        // Created only through getInstance().
    }

    public static synchronized UserSession getInstance() {
        if (instance == null) {
            instance = new UserSession();
        }
        return instance;
    }

    public void startRegisteredSession(int userId, String username) {
        if (userId <= 0) {
            throw new IllegalArgumentException("A registered session needs a real user ID");
        }
        this.userId = userId;
        this.username = username;
        this.guest = false;
    }

    public void startGuestSession() {
        this.userId = GUEST_USER_ID;
        this.username = "Guest";
        this.guest = true;
    }

    public void endSession(DatabaseHelper databaseHelper) {
        if (guest && databaseHelper != null) {
            databaseHelper.clearGuestData();
        }
        userId = NO_USER_ID;
        username = null;
        guest = false;
    }

    // True when a registered user or a guest is currently logged in
    public boolean isActive() {
        return userId != NO_USER_ID;
    }

    public boolean isGuest() {
        return guest;
    }

    // True when the session belongs to a real account in user_data
    public boolean isRegisteredUser() {
        return isActive() && !guest;
    }

    public int getUserId() {
        return userId;
    }

    public String getUsername() {
        return username;
    }
}

@Override

    // in cannot get the previous session.

// Registered login: validate, look up the ID, open the session
private void loginUser() {
    String username = editTextUsername.getText().toString().trim();
    String password = editTextPassword.getText().toString();

    if (username.isEmpty() || password.isEmpty()) {
        Toast.makeText(this, "Enter a username and password", Toast.LENGTH_SHORT).show();
        return;
    }

    int userId = databaseHelper.getUserIdForCredentials(username, password);
    if (userId == UserSession.NO_USER_ID) {
        Toast.makeText(this, "Invalid username or password", Toast.LENGTH_SHORT).show();
        return;
    }

    UserSession.getInstance().startRegisteredSession(userId, username);
    openDataDisplayActivity();
}

// Guest login: creates a temporary session that is never tied to an account
private void loginAsGuest() {
    UserSession.getInstance().startGuestSession();

    // Start clean so one guest never sees a previous guest's entries.
    databaseHelper.clearGuestData();

    Toast.makeText(this, "Guest session started. Entries are not saved.",
            Toast.LENGTH_SHORT).show();
    openDataDisplayActivity();
}

Code highlights

  • Registered sessions require a real user ID, and guests get a reserved ID (GUEST_USER_ID), so guest rows never mix with account rows.
  • Login code builds the session first (startRegisteredSession or startGuestSession), then opens the data screen with no intent extras needed.
  • The data screen checks session.isActive() and exits if someone reached it without logging in.
  • loadRecords() asks the database only for records that belong to session.getUserId().
  • Deleting uses selected.getId() from the record object, and the user ID is passed along too, so only the current user's data can be removed.
  • endSession() clears guest rows before resetting the session, and the login screen calls it in onResume(), so logout and fresh launches both start with no active user.

Enhancement 2: Algorithms and Data Structures

Narrative for Enhancement 2: https://github.com/CoopDavidSNHU/cs499-project/blob/main/assets/Module-4-Assessment-CS-499.pdf

The weight history was shown in whatever order SQLite returned rows, which is insertion order rather than date order. I added a WeightRecordSorter class that sorts a list of WeightRecord objects by parsing each record's date. It repeats passes over the list, swapping neighboring records that are out of order, until a pass makes no swaps (a bubble sort). That is O(n^2) in the worst case, which is fine for a personal weight history. Dates that cannot be parsed are sorted to the end instead of crashing the sort or disappearing from the list.

WeightRecordSorter.java (excerpt)

public static void sortChronologically(List<WeightRecord> records) {
    if (records == null || records.size() < 2) {
        return;
    }

    boolean exchanged;
    do {
        exchanged = false;
        // FOR each record in the list: compare its date with the next
        // record's date, if the current one is later, exchange them.
        for (int i = 0; i < records.size() - 1; i++) {
            Date currentDate = parseDate(records.get(i).getDate());
            Date nextDate = parseDate(records.get(i + 1).getDate());

            if (shouldSwap(currentDate, nextDate)) {
                WeightRecord temp = records.get(i);
                records.set(i, records.get(i + 1));
                records.set(i + 1, temp);
                exchanged = true;

            }
        }
        // Continue comparisons until records are ordered oldest to newest.
    } while (exchanged);
}

private static boolean shouldSwap(Date current, Date next) {
    if (current == null) {
        return next != null;
    }
    if (next == null) {
        return false;
    }
    return current.before(next);
}

private static Date parseDate(String dateText) {
    if (dateText == null) {
        return null;
    }
    // yyyy-mm-dd matches the format used by the add data dialog's hint
    // and by already existing entries (following format: "2026-10-02").
    SimpleDateFormat format = new SimpleDateFormat("yyyy-MM-dd", Locale.US);
    format.setLenient(false);
    try {
        return format.parse(dateText.trim());
    } catch (ParseException e) {
        return null;
    }
}

Code highlights

  • The do while loop keeps making passes until the list is fully ordered.
  • shouldSwap() compares the two dates and puts unparseable dates last, so bad data never breaks the list.
  • parseDate() uses a strict yyyy-MM-dd format that matches the add-entry dialog's hint.
  • The sorter is a small utility class called from one place, loadRecords(), so the screen code stays simple.

I made four improvements to the database layer without rewriting the project. First, credentials now come from environment variables instead of being hard-coded, with a clear error that names any missing variable (never its value). Second, I added indexes for the fields the dashboard filters on: one compound index ordered to match the rescue queries, plus single-field indexes for breed and age. Third, the rescue-type rules moved out of the dashboard and into the database layer. Fourth, filtering and the age calculations moved out of Pandas and into a MongoDB aggregation pipeline, so the database returns only the records and fields the dashboard needs.

    def __init__(self):
        # Credentials come from environment variables, never from source code.
        # .strip() guards against stray spaces copied into the variable.
        USER = (os.environ.get("MONGO_USER") or "").strip()
        PASS = (os.environ.get("MONGO_PASSWORD") or "").strip()
        HOST = (os.environ.get("MONGO_HOST") or "").strip()
        PORT = (os.environ.get("MONGO_PORT") or "").strip()  # optional, isn't used with mongodbAtlas

        DB = 'NEWAAC'
        COL = 'animals'

        # Report which variables are missing (names only, never values)
        missing = [
            name for name, value in (
                ("MONGO_USER", USER),
                ("MONGO_PASSWORD", PASS),
                ("MONGO_HOST", HOST),
            ) if not value
        ]
        if missing:
            raise ValueError(
                "MongoDB environment variables are not configured: "
                + ", ".join(missing)
            )

        # Hide special characters
        user = quote_plus(USER)
        password = quote_plus(PASS)

        if PORT:
            # Standard connection (local or self-hosted MongoDB)
            uri = f"mongodb://{user}:{password}@{HOST}:{PORT}/"
        else:
            # Atlas style connection (host only, no port allowed)
            uri = f"mongodb+srv://{user}:{password}@{HOST}/?appName=Cluster0"

        # Initialize Connection (fail fast after 5 seconds if the server is unreachable)
        self.client = MongoClient(uri, serverSelectionTimeoutMS=5000)
        self.database = self.client[DB]
        self.collection = self.database[COL]

        # Make sure the indexes used by the dashboard queries exist
        self._ensure_indexes()

animal_shelter.py: indexes

    def _ensure_indexes(self):
        """
        Create indexes for the fields the dashboard filters on.
        """
        try:
            # Compound index is ordered in this way: exact match -> $in match -> range.
            # That order matches the rescue queries, so MongoDB can narrow
            # the search at each step instead of scanning every document.
            # It also serves queries on sex_upon_outcome alone,
            # so a separate single field sex index wouldn't be needed.
            self.collection.create_index(
                [
                    ("sex_upon_outcome", ASCENDING),
                    ("breed", ASCENDING),
                    ("age_upon_outcome_in_weeks", ASCENDING),
                ],
                name="rescue_compound_idx",
            )

            # Single field indexes for queries that don't use the compound prefix
            self.collection.create_index(
                [("breed", ASCENDING)], name="breed_idx"
            )
            self.collection.create_index(
                [("age_upon_outcome_in_weeks", ASCENDING)], name="age_weeks_idx"
            )
        except Exception as e:
            # For example, the database user might not have createIndex privileges
            print(f"Could not confirm indexes: {e}")

animal_shelter.py: aggregation pipeline

    @staticmethod
    def _build_match(rescue_type):
        """Translate a rescue type into a MongoDB filter ({} matches everything)."""
        rule = RESCUE_FILTERS.get(rescue_type)

        # "All", None, or an unknown type -> empty filter
        if rule is None:
            return {}

        # Age range: always a lower bound, upper bound only if defined
        age = {"$gte": rule["min_weeks"]}
        if rule["max_weeks"] is not None:
            age["$lte"] = rule["max_weeks"]

        return {
            "sex_upon_outcome": rule["sex"],
            "breed": {"$in": rule["breeds"]},
            "age_upon_outcome_in_weeks": age,
        }

    def build_pipeline(self, rescue_type=None):
        """
        Build the aggregation pipeline:
          $match   - filter documents
          $project - keep only needed fields and calculate age values
        """
        # Safely convert the stored age to a number (null if conversion fails)
        weeks = {
            "$convert": {
                "input": "$age_upon_outcome_in_weeks",
                "to": "double",
                "onError": None,
                "onNull": None,
            }
        }

        # Start by excluding _id, then include only the dashboard fields
        project = {"_id": 0}
        for field in DASHBOARD_FIELDS:
            project[field] = 1

        # Calculated fields, ran by MongoDB instead of Pandas
        project["age_in_weeks"] = weeks
        project["age_in_years"] = {
            "$round": [{"$divide": [weeks, WEEKS_PER_YEAR]}, 1]
        }

        return [
            {"$match": self._build_match(rescue_type)},
            {"$project": project},
        ]

    def read_rescue_filter(self, rescue_type=None):
        """
        Server side filtering and age calculation for the dashboard.
        rescue_type: "Water", "Mountain", "Disaster", or None/"All" for everything.
        Returns a list of dictionaries the dashboard can use directly.
        """
        try:
            return list(self.collection.aggregate(self.build_pipeline(rescue_type)))
        except Exception as e:
            print(f"An error has occurred: {e}")
            return []  # Empty list keeps the dashboard from crashing

Code highlights

  • The credentials come from os.environ and quote_plus escapes special characters, so nothing sensitive lives in the source code or on GitHub.
  • The connection works for both a standard host and port and an Atlas-style URI, and fails fast after 5 seconds if the server is unreachable.
  • The compound index is ordered exact match, then $in match, then range, which matches how the rescue queries filter and also covers queries on sex alone.
  • _build_match() turns each rescue type into a MongoDB filter, with max_weeks = None meaning no upper age limit.
  • $match runs first so MongoDB can use the indexes, and $project keeps only the dashboard fields and calculates age_in_weeks and age_in_years on the server.
  • If a query fails, read_rescue_filter() returns an empty list so the dashboard doesn't crash.
  • Testing plan: compare the original query, the indexed query, and the aggregation, checking records, fields, filtering, and dashboard behavior.
